# 저가 모델 실행 지침 — 미해결 과제

이 문서는 작은 모델이 한 번에 한 과제만 안전하게 수행하도록 만든 실행서다. 전체 우선순위와 배경은 `OPEN-TASKS-2026-09-10.md`에 있다. 이 문서에서는 배경을 다시 판단하지 말고 아래 게이트를 순서대로 통과한다.

## 공통 실행 계약

### 작업 시작

1. `CLAUDE.md`를 읽는다.
2. `git status --short`를 실행한다.
3. 사용자 파일 `.claude/settings.local.json`, `docs/PRESENTATION-2026-09-16.md`, `docs/PRESENTATION-2026-09-16.pptx`를 수정·삭제·커밋하지 않는다.
4. 아래 작업 카드 하나만 고른다. 카드의 완료 기준을 충족하기 전 다른 카드로 넘어가지 않는다.
5. 첫 보고에 `카드 ID`, `변경 예정 파일`, `DB 쓰기 여부`, `외부 API 호출 여부`를 적는다.

### 증거 규칙

- `확인`: 명령 출력, 코드, 운영 DB 조회, 운영 화면에서 직접 본 결과만 사용한다.
- `추정`: 확인하지 못한 설명에는 반드시 `추정`이라고 쓴다.
- 과거 문서의 행 수와 날짜는 현재값이 아니다. 현재 운영 수치는 다시 조회한다.
- 원인을 정하기 전에 반증 조회를 하나 수행한다. 예: 단위 오류라면 값의 비율이 10배 이상 벌어지는지 본다.
- 로그와 명령 출력에 키 값을 출력하지 않는다. 환경변수의 존재는 실제 작업 성공 여부로 확인한다.

### 변경 규칙

- 파일 편집 전 대상 함수와 기존 회귀 검사를 `rg`로 찾는다.
- 한 카드에서 요구한 파일만 수정한다. 범위 밖 결함은 `후속 과제`로 기록한다.
- 운영 `UPDATE` 또는 `DELETE` 전 같은 조건의 `SELECT` 결과를 사람이 읽을 수 있게 제시한다.
- 스키마 변경은 `supabase/`에 재실행 가능한 SQL을 만든다. SQL Editor 적용은 코드 완료와 구분해 보고한다.
- 기사·이벤트·청크의 수를 같은 단위처럼 비교하지 않는다. `knowledge_chunk`는 `source_type`별로 센다.
- 검사 실패를 우회하거나 기대값을 낮춰 통과시키지 않는다. 실패 원인을 고치거나 `중단`으로 보고한다.

### 공통 검증

JavaScript를 수정했으면 수정 파일마다 `node --check <파일>`을 실행한다. 그 뒤 아래를 실행한다.

```powershell
npm run check
git diff --check
```

`lib/` 또는 `api/`를 수정했으면 모든 회귀 검사를 실행한다.

```powershell
Get-ChildItem scripts/check-*.mjs | ForEach-Object { node $_.FullName; if ($LASTEXITCODE -ne 0) { throw "FAILED: $($_.Name)" } }
```

## C0. 현재 상태와 평가 기준선 확보

### 목표

검색 또는 청크를 바꾸기 전에 현재 품질과 운영 잔량을 기록한다.

### 입력

- `docs/HANDOFF-CODEX.md`의 P1~P4, N1 기대 결과
- 관리자 화면 `/admin`의 `RAG 평가 → 평가 세트`
- 테이블 `rag_eval_case`, `rag_eval_run`, `rag_eval_result`

### 절차

1. 운영 관리자 화면에서 기존 평가 문항을 읽는다. 같은 `question + company_id + include_unverified`가 있으면 새로 만들지 않는다.
2. 다음 문항이 없으면 등록한다. 회사 필터는 전부 비우고, 보조 데이터는 끈다.

| ID | 질문 | 기대 결과 |
|---|---|---|
| P1 | `byd 2022년 이후 연도별 매출을 알려줘` | 2022~2025 네 기간, BYD만, 정량 조회 |
| P2 | `전고체 배터리를 하고 있는 기업?` | 서로 다른 회사 3곳 이상; 직접 근거와 참고를 구분 |
| P3 | `CATL 사업 추진 현황` | 서로 다른 기사에서 주제 5개 이상; 불리한 사실도 포함 |
| P4 | `초급속 충전 기술 혹은 제품을 가진 회사` | 셀사와 소재사가 함께 나오고 역할이 구분됨 |
| N1 | `셀사의 LFP 생산 캐파` | 소재사를 셀사로 답하지 않음; 셀사 근거가 없으면 없다고 표시 |

3. 각 문항의 정답 청크를 확정할 수 없으면 `reference_chunk_ids=[]`로 두고 기대 결과를 `reference_answer`에 구체적으로 적는다. 빈 정답 청크로 계산된 Hit@10·MRR·Recall@10을 유효한 검색 점수라고 보고하지 않는다.
4. `benchmark-run`을 한 번 실행한다. 실행 ID, 시각, 문항 수, 문항별 상위 10개를 기록한다.
5. P1~P4는 기업 분석 화면에서도 실행한다. P1의 기간·회사, P2~P4의 회사 수·기사 수·주제 수를 수기로 기록한다.
6. N1의 현재 실패 형태를 기록한다. 수정은 C2에서 한다.
7. 다음 잔량을 읽기 전용으로 센다: `knowledge_chunk`의 source_type별 행 수와 고유 기사/이벤트 수, `embedding_status='failed'`, 미완료 report_digest/갱신 상태. 접근 수단이 없으면 숫자를 추측하지 않고 `미확인`으로 적는다.

### 중단 조건

- 평가 테이블이 없거나 저장 요청이 오류면 오류 본문을 기록하고 중단한다.
- 정답 청크를 정하지 않은 문항의 점수를 품질 기준선으로 사용할 수 없다. 실화면 관찰만 기준선으로 남긴다.
- 운영 검색 결과를 얻기 전에 `lib/knowledge-search.js`, 청크 형식, 임베딩을 변경하지 않는다.

### 완료 기준

- 다섯 문항이 중복 없이 존재한다.
- 실행 ID와 문항별 결과가 저장됐다.
- P1~P4 실화면 결과와 N1 실패가 한 문서 또는 평가 답안에 기록됐다.
- 현재 운영 잔량은 `확인` 또는 `미확인`으로 구분됐다.

## C1. 정량 표 단위와 계정 오선택 수정

### 목표

`[单位:千元]` 같은 표 꼬리표를 무시해 값이 1000배 작아지는 오류와 자회사·제품 매출을 전사 매출로 고르는 오류를 막는다.

### 허용 범위

- `lib/report-metrics.js`
- `scripts/check-report-metrics.mjs` 또는 이 기능을 검사하는 기존 `check-*.mjs`
- 필요할 때 읽기 전용 `scripts/crosscheck-report-metrics.mjs`

### 고정 재현 사례

```text
营业收入合计 | 423,701,834 | 100.00% | 362,012,554 | 100.00% | 17.04% [单位:千元]
```

기대값: `revenue_total = 4237.01834 CNY_100M`. `4.237...`이면 실패다.

다음 문구는 전사 매출로 선택하면 실패다.

```text
子公司金驰能源材料有限公司营业收入
负极材料实现营业收入
```

### 절차

1. `rg -n "单位|SEGMENT_PREFIX|营业收入|extractMetrics" lib/report-metrics.js scripts/check-*.mjs`로 현재 로직과 검사를 찾는다.
2. 코드를 바꾸기 전에 위 세 사례를 검사에 추가해 실패를 확인한다. 기존 검사 파일이 목적에 맞으면 그 파일에 추가한다.
3. 표 꼬리표의 단위를 같은 행 숫자의 단위로 사용한다. 본문 단위와 꼬리표가 충돌하면 숫자를 저장하지 않는 명시적 결과를 선택하고 검사한다.
4. 회사·자회사·제품·사업부 수식어가 붙은 매출을 전사 `revenue_total` 후보에서 제외한다. `营业总收入` 또는 문맥상 전사 합계인 행은 유지한다.
5. 고정 사례와 전체 회귀 검사를 실행한다.
6. 운영 환경이 있으면 쓰기 없이 실행한다.

```powershell
node --env-file=.env.local scripts/backfill-report-metrics.mjs
node --env-file=.env.local scripts/crosscheck-report-metrics.mjs
```

환경 파일 이름이 실제 구성과 다르면 존재하는 파일을 확인하되 내용을 출력하지 않는다.
7. 교차 대조에서 이탈을 각각 `수정됨`, `계정 범위 차이`, `제공자 값 차이`, `원인 미확정`으로 분류한다. 원문 공시의 계정명·값·기간이 거래소 제공값과 다르면 원문 추출값을 덮어쓰지 않는다.

### 중단 조건

- `backfill-report-metrics.mjs --write`는 이 카드에서 실행하지 않는다.
- 단위 꼬리표의 적용 범위를 결정할 수 없는 입력은 억지로 환산하지 않는다.
- 거래소 값과 다르다는 이유만으로 추출값을 거래소 값으로 덮어쓰지 않는다.

### 완료 기준

- 고정 단위 사례가 정확히 4237.01834로 파싱된다.
- 자회사와 제품 매출 사례가 `revenue_total`로 저장되지 않는다.
- 전체 회귀가 통과한다.
- 읽기 전용 교차 대조 결과와 이탈별 판정이 보고됐다.

### 2026-09-10 실행 기록

- 창위안리커 2024 자회사 매출과 샹타이 2023 음극재 제품 매출은 전사 `revenue_total` 오선택으로 확정했다. 대상 행 2건을 `outputs/c1-report-metric-backup-2026-09-10.json`에 백업한 뒤 삭제했다.
- XTC 2024 연간·반기 매출은 공시 `营业收入`과 Eastmoney `营业总收入`의 계정 범위 차이로 분류했다.
- XTC 2024 지배주주 순이익 4.940738억 위안 및 Lopal 2024 지배주주 순이익 -6.356681억 위안은 공시 원문과 일치한다. Eastmoney 값과의 차이는 제공자 값 차이로 남기며, 원문 행은 유지한다.
- 삭제 뒤 읽기 전용 대조는 141개 중 137개가 ±1% 이내였고, 남은 4건은 위 원문·제공자 차이다.

## C2. 밸류체인 회사 범위 검색

### 목표

`셀사`, `양극재 회사`, `음극재 회사`를 회사 마스터의 `type_tags` 집합으로 해석한다. 주제어 의미는 유지한다.

### 허용 범위

- `lib/knowledge-search.js`
- 회사 마스터를 읽는 기존 모듈
- `scripts/check-search-plan.mjs`와 관련 검색 회귀

### 절차

1. C0 기준선이 있는지 확인한다. 없으면 코드 변경 없이 중단한다.
2. 현재 회사 마스터에서 `type_tags`별 활성 회사 ID를 코드로 읽는다. 문서에 적힌 10·13·9개를 하드코딩하지 않는다.
3. N1이 어떤 `requiredTerms/requiredGroups`를 만드는지 검사로 재현한다.
4. 세그먼트 표현을 회사들의 필수 OR 그룹으로 변환한다. 명시 회사 질문과 그룹 계열사 검색에 쓰는 기존 `requiredGroups` 흐름을 재사용한다.
5. `양극재`가 소재 주제어로 쓰인 질문과 `양극재 회사`처럼 회사 범위를 뜻하는 질문을 각각 검사한다.
6. 긴 OR 그룹에 대해 생성 질의 길이와 검색 시간을 기록한다. 검색 오류 또는 기준선 대비 2배 초과 지연이면 확대하지 않고 중단한다.
7. N1과 P1~P4를 다시 실행해 C0 결과와 비교한다.

### 필수 검사

- N1 결과의 회사는 모두 `type_tags`에 `cell`이 있다.
- 셀사 근거가 0건이면 다른 세그먼트 근거로 답을 만들지 않는다.
- P2와 P4의 서로 다른 회사 수가 C0보다 줄지 않는다.
- P1은 BYD 이외 회사의 정량 행을 포함하지 않는다.
- P3은 기사당 상위 청크 제한과 그룹 계열사 확장을 유지한다.

### 완료 기준

필수 검사와 전체 회귀가 통과하고, C0 대비 결과표가 보고됐다.

## C3. 기사 청크 5건 시범 재구성

### 목표

요약 중복을 제거한 새 청크 형식의 검색 효과를 5기사에서 측정하고 확대 여부를 결정한다.

### 선행 조건

- C0 완료
- 새 청크와 기존 청크의 임베딩을 포함한 백업 또는 재임베딩 없는 복구 절차가 실제로 준비됨
- 운영 엔드포인트 또는 유효한 Supabase/OpenAI 환경 중 하나가 준비됨

### 절차

1. dry-run만 실행한다.

```powershell
node --env-file=.env.local scripts/restructure-article-chunks.mjs
```

2. 출력에서 변경 기사 수, 기존/예상 청크 수, 이미 새 형식인 기사 수를 기록한다. 과거 기록의 188건과 다르면 현재 출력을 사용한다.
3. 변경할 정확한 5개 기사 ID와 해당 기존 청크를 SELECT해 검토한다. 가능하면 P2~P4 검색에 실제 등장하는 기사를 포함한다.
4. 해당 5기사의 기존 청크 행을 임베딩까지 백업하고 복구 SQL 또는 복구 스크립트를 실제로 검증한다.
5. 로컬 스크립트를 쓸 때 확인된 명령은 다음뿐이다.

```powershell
node --env-file=.env.local scripts/restructure-article-chunks.mjs --apply --limit 5
```

운영 엔드포인트를 쓸 때는 preview와 limit 지원 여부를 코드에서 확인한 뒤 같은 5기사 범위만 실행한다.
6. 실행 후 그 5기사의 새 청크가 먼저 저장됐고 옛 청크만 제거됐는지 SELECT로 확인한다.
7. C0과 같은 문항으로 평가를 다시 실행한다.

### 확대 판정

- `확대`: P1~P4 필수 조건이 유지되고, 중복 기사 독점이 감소하며, 관련 청크 순위가 개선 또는 동일하다.
- `복구`: 필수 조건 하나라도 깨지거나 관련 청크가 사라진다.
- `보류`: 정답 청크가 없어 개선 여부를 계산할 수 없다. 5건을 더 처리하지 않는다.

### 완료 기준

5기사 전후 행 수, 평가 실행 ID, 품질 비교, 확대/복구/보류 판정이 모두 기록됐다. 전량 실행은 별도 카드로 승인받는다.

## C4. 보고서 갱신과 이벤트 재임베딩

### 목표

새 추출 규칙으로 보고서를 갱신한 뒤 살아남은 이벤트만 현재 형식으로 재임베딩한다.

### 선행 조건

- C1 완료
- T1의 고정 PDF 표본에서 날짜·근거·다중 행 표의 정확도 확인
- 갱신 대상 SELECT와 기존 이벤트 백업 완료

### 절차

1. 갱신 큐의 현재 대상 수와 상태별 수를 SELECT한다.
2. 완룬 고정 표본을 dry-run해 반환 수, day/month/half/year 정밀도, badDate, empty, 실패 조각 수를 기록한다.
3. 실제 다중 행 표 3개 이상을 원문과 대조한다. 열 또는 단위가 틀리면 갱신 쓰기를 중단하고 표 복원 과제로 넘긴다.
4. 보고서 1건만 갱신한다. 새 추출이 3건 이상, 기존의 50% 이상이며 실패 조각이 0일 때만 교체 경로가 작동하는지 확인한다. 그 외에는 기존 이벤트가 유지돼야 한다.
5. 갱신 결과의 `source_sha256`, `parse_quality`, `visual_pages`, `renewal_status`를 확인한다.
6. 작은 배치로 확대하고 매 배치 뒤 성공·부분 성공·timeout·실패 수를 기록한다.
7. 최종 이벤트 집합이 안정된 뒤 재임베딩 건수 확인을 실행한다.

```powershell
node --env-file=.env.local scripts/reembed-events.mjs
```

8. 대상 이벤트 수와 기존 `event_fact` 청크 수가 같을 때만 적용한다.

```powershell
node --env-file=.env.local scripts/reembed-events.mjs --apply
```

### 중단 조건

- 재임베딩 전후 건수가 다르면 즉시 중단한다.
- 조각 실패가 있는 보고서의 기존 이벤트를 교체하지 않는다.
- 반복 timeout 정책이 구현·검사되지 않았으면 대량 갱신을 시작하지 않는다.

### 완료 기준

갱신 대상별 결과와 재임베딩 전후 동일 건수가 기록되고, 전체 회귀가 통과한다.

## C5. 새 보고서 뒤 정량 자동 갱신

### 목표

보고서 이벤트가 저장된 뒤 그 회사·기간의 `report_metric`을 자동 갱신한다.

### 선행 조건

C1과 C4 완료.

### 절차

1. 보고서 저장 성공 지점을 찾고, 해당 보고서의 회사·source_url·기간을 식별한다.
2. 전량 백필 대신 해당 보고서 이벤트만 `extractMetricsFromEvents()`에 전달한다.
3. 같은 `company_id, period, metric`을 upsert한다. 부분 추출 실패 시 기존 정상 행을 지우지 않는다.
4. 신규 보고서 1건, 동일 보고서 재실행, 지표 0건 보고서, 부분 실패의 네 사례를 검사한다.
5. CATL 2025 같은 늦게 도착한 보고서를 고정 사례로 사용해 이벤트 저장 뒤 정량 칸이 채워지는지 확인한다.

### 완료 기준

신규 도착 뒤 자동으로 정량 칸이 채워지고 재실행 시 중복되지 않으며 실패 시 기존 값이 유지된다.

## C6. 운영 자동화 점검

### 목표

최근 3일의 실제 로그로 무인 실행 성공 여부와 남은 실패를 판정한다. 코드는 원인이 확인된 경우에만 수정한다.

### 절차

1. `pipeline_log`에서 최근 3일 실행을 trigger/run별로 묶는다.
2. 각 실행에서 collect, process, daily, curate의 시작·종료·duration_ms·error·chain_depth를 표로 만든다.
3. 다음을 별도 집계한다: bootstrap_ids, `web_search_bootstrap_*` 기사 수, Reshine/Kaijin 웹 원장, embedding failed/attempts, 검색 재작성 발동 수와 응답시간.
4. 실패마다 로그가 지지하는 원인과 반증 조회를 한 쌍으로 기록한다.
5. 300초를 넘은 행, depth cap, 반복 timeout이 있으면 해당 경로만 수정 카드로 분리한다.

### 완료 기준

3일 × 필수 단계의 성공표와 실패별 근거가 있다. 데이터가 3일 미만이면 `관찰 부족`으로 보고하고 성공 선언을 하지 않는다.

## C7. 원문 기반 품질 검증

### 목표

벡터 지식의 발췌·사실·숫자·날짜를 원문과 대조한다.

### 절차

1. `docs/VECTOR-VERIFICATION-PLAN.md`의 2단계 표본 규칙으로 60건을 뽑는다. 금액, 날짜, 다중 행 표, 이미지 페이지를 포함한다.
2. URL 원문을 다시 확보하고 발췌 축자 일치, 사실 지지, 숫자 정합성, 날짜 규약을 각각 판정한다.
3. 원문을 확보하지 못한 건은 오답과 섞지 않고 `검증불가`로 집계한다.
4. 자동 결과 뒤 사람 검수 20건을 수행한다.
5. 기준을 계산한다: 발췌 98%, 사실 지지 90%, 숫자 95%, 날짜 100%, 자동·사람 일치 80%.

### 완료 기준

분모·분자를 포함한 지표, 실패 표본 ID, 실패 유형, 다음 수정 카드가 기록됐다.

## 후속 카드 생성 템플릿

다중 회사 귀속, 일반 공시 분석, 다중 행 표 복원, 사업 관계망, 그룹 마스터 확장은 위 카드가 끝난 뒤 각각 별도 카드로 작성한다. 아래 항목이 하나라도 비면 구현을 시작하지 않는다.

```text
카드 ID와 한 문장 목표
선행 조건
입력 데이터와 고정 재현 사례
수정 허용 파일
DB 쓰기와 외부 호출 여부
번호가 있는 실행 절차
필수 회귀 사례
중단 조건
수치로 확인 가능한 완료 기준
최종 보고 형식
```

# 미해결 과제와 실행 순서 — 2026-09-10

이번 문서는 실행 계획과 진행 기록이다. C0 기준선, C1·C2 코드 수정, C3 기사 5건 시범 재구성까지 실행했으며 나머지 운영 DB 변경·재임베딩·배포는 실행하지 않았다. 근거는 HANDOFF-CODEX.md, HANDOFF.md, PLAN-embedding-recovery.md와 현재 코드다. 운영 수치는 단계별 실행 시점에 재조회한다. 아래 합격 기준 중 기존 문서에 없는 것은 이번 계획의 제안이다.

저가 모델 또는 별도 에이전트에 과제를 맡길 때는 `LOW-COST-MODEL-RUNBOOK.md`에서 카드 하나만 전달한다. 여러 카드를 한 번에 맡기지 않는다.

## 실행 순서

### 1. 현재 상태와 검색 기준선 확보

- 운영 DB에서 평가 문항·평가 실행·SQL 적용 상태, source_type별 청크 수, 갱신·임베딩 실패 잔량을 읽기 전용으로 확인한다. 과거 기록의 188기사·107보고서를 현재 작업량으로 확정하지 않는다.
- 사용자가 만족한 P1~P4(BYD 연도별 매출, 전고체 기업, CATL 추진 현황, 초급속 충전 기업)와 실패한 N1(셀사의 LFP 생산 캐파)을 평가 세트에 등록한다. 최근 평가 화면 수정 이후 실제 등록 여부부터 확인해 중복 등록을 피한다.
- 기대 기사·회사·기간을 지정하고 검색 결과와 Hit@10·MRR·Recall@10을 저장한다. 정량 조회 P1과 최종 답변의 역할 구분·주제 다양성은 별도 실화면 평가로 남긴다. 검색 평가 숫자만으로 답변 품질을 판정하지 않는다.
- T6의 기존 5문항·42건 사람 판정도 비교 자료로 유지한다. 정량 행 평가의 FK 수정 SQL(U6)은 실제 적용 여부와 저장 성공을 확인한다.
- 완료: 반복 가능한 평가 기록, 문항별 기대 결과, 현재 운영 잔량이 확보된다. 이 전에는 검색 순위·청크 형식을 변경하지 않는다.

### 2. 정량 데이터의 오류 유입 차단

- T8: 표 끝의 `[单位:千元]`, `[单位:万元]`를 환산에 반영하는지 실제 파서로 재현한다. 단위 누락·충돌은 추정값 저장 대신 검토 대상으로 분리한다.
- T7 완료: 창위안 자회사 매출과 샹타이 제품 매출의 전사 매출 오선택 2행을 백업 후 삭제했다. XTC 2024 연간·반기 매출은 공시 `营业收入`과 Eastmoney `营业总收入`의 계정 범위 차이다. XTC와 Lopal의 지배주주 순이익은 각각 공시 원문과 일치하므로 Eastmoney 제공값 차이로 보류한다. 거래소 집계값에 맞추기 위해 원문 추출값을 덮어쓰지 않는다.
- 실제 발췌를 고정 사례로 검사 → 쓰기 없는 백필 → 교차 대조 → 변경 대상 SELECT → 검증된 행만 반영한다.
- 완료: 단위·비율 회귀 사례 통과, 기존 이탈 6칸 각각의 처리 근거 기록, 신규 단위 오염 0건. T8 통과 전 정량 백필 쓰기는 금지한다.

### 3. 밸류체인 질문 수정

- N1을 먼저 재현한다. `셀사`를 회사 마스터의 cell 집합으로 해석하고 양극재·음극재도 회사 범위 의도와 소재 주제 의도를 구분한다.
- 기존 requiredGroups를 활용하되 활성 추적 회사 범위와 긴 OR 질의의 결과·지연을 검증한다.
- 완료: N1에서 소재사 근거로 셀 생산능력을 답하지 않는다. 셀사 자료가 없으면 그 공백을 명시한다. P1~P4의 회사·기간·주제 다양성이 유지된다.

### 4. 데이터 재처리 — 세 종류를 분리

각 작업은 별도 변경으로 평가한다. 대상 SELECT → 원본·임베딩·연결 데이터 백업 → 복구 가능성 확인 → 소량 실행 → 전후 평가 → 확대 순서다. 기사 수와 청크 수를 혼동하지 않는다.

1. **T15 기사 청크 재구성:** 기록상 구형 188기사. 2026-09-10에 5기사(2·3·1·1·7청크)를 백업 후 재구성했고 실패 0건이었다. 기준 청크 19건을 연결해 전후 평가한 결과 Hit@10·Recall@10은 1.00으로 유지되고 MRR은 0.84→1.00이었으나, 변경 기사가 상위 10개에 직접 등장하지 않았고 중복 기사 독점 감소도 보이지 않았다. 판정은 `보류`다. 다음 시범은 중복이 실제 상위 검색을 독점하는 기사 5건을 대상으로 다시 선정한다.
2. **T1/T3 보고서 추출·갱신:** 다중 행 표와 날짜가 명시된 사건을 원문 대조한다. 완룬 등 고정 표본에서 정확도와 재현율을 함께 확인하고 갱신 큐를 처리한다. 부분 실패가 있으면 기존 정상 사실을 대체하지 않는다. 반복 timeout 상한과 다음 보고서로 넘어가는 동작도 확인한다.
3. **T2 이벤트 재임베딩:** 시점 정밀도·근거·상대방을 포함하는 새 형식을 최종 이벤트에 반영한다. 보고서 갱신으로 지워질 이벤트를 먼저 전량 재임베딩하지 않는다.

완료: 범위별 성공·실패·보류 수, 품질 변화, 복구 방법이 남는다. 운영 키를 쓰는 기사 재구성 경로는 이미 있으므로 로컬 키 문제가 모든 작업을 막는다고 보지 않는다.

### 5. 새 데이터와 정량 갱신 연결

- T9: 보고서 이벤트 저장 후 해당 회사·기간의 정량 추출이 실행되도록 연결한다. 2단계 완료 후 적용한다.
- 반복 실행의 중복 방지, 부분 실패 재시도, 완료 상태 기록을 확인한다.
- 완료: 새 보고서 도착 후 수동 전량 백필 없이 해당 정량 칸이 채워지고, 재실행해도 정상 값이 중복·훼손되지 않는다.

### 6. 운영 자동화의 실효성 확인

- 최근 야간 로그에서 수집 → 본문 → Daily → curate 완료와 실패·깊이 상한 중단을 확인한다. 과거의 60초 가정으로 원인을 정하지 않는다.
- Reshine·Kaijin bootstrap 기사 유입과 웹 백필 원장·90일 순환 반영을 확인한다. Kaijin 12건 상한의 누락은 실제 자료와 비교한다.
- 임베딩 자동 재시도는 이미 코드가 있으므로 실패 잔량·재시도 소진·복구 결과를 점검한다.
- 검색 재작성 fallback의 발동률·응답시간·추가 호출 비용을 측정한다. 무작정 재시도 수를 늘리지 않는다.
- 완료: 3일 연속 무인 실행에서 필요한 단계가 완료되고, 잔여 실패마다 원인·재시도 또는 보류 상태가 설명된다.

### 7. 원문 기반 품질 검증

- VECTOR-VERIFICATION-PLAN의 원문 대조 60건 → 사람 검수 20건을 진행한다. 금액·단위·날짜·다중 행 표를 포함한다.
- 기존 기준: 발췌 일치 98% 이상, 사실 지지 90% 이상, 숫자 정합성 95% 이상, 날짜 규약 100%. 출처를 다시 확보하지 못한 사례는 별도 집계한다.
- report_chunk 확대(T5)는 이미지 도표 누락률과 표 정확도를 본 후 결정한다.

## 오래된 기록에서 제외하거나 정정할 항목

- BYD 열린 연도 범위, 정량 사전조회, 검색 재작성 회사 이탈 차단, 관리자 게이트는 후속 완료 기록이 있다. 신규 구현이 아니라 회귀 검증 대상이다.
- HKEX 수집기는 lib/report-reader.js에 구현돼 있다. '경로 없음'을 신규 개발 과제로 잡지 않는다.
- 임베딩 실패 재시도도 lib/curation.js에 구현돼 있다. 운영 효과 확인이 남는다.
- 평가 세트·무료 검색 평가 실행은 구현 완료다. 문항 등록과 실제 평가 기록이 남았는지는 재확인이 필요하다. 'LLM 호출 없음'이 검색 임베딩 비용까지 0이라는 뜻은 아니다.
- plan.md의 초기 MVP·사람 승인·시드 데이터 설명은 현재 운영 계획으로 사용하지 않는다.

## 실행 범위와 검증

추천 첫 묶음은 1단계 기준선 확보와 2단계 정량 오류 재현·수정이다. 이어 3단계를 독립 변경으로 검증하고 4단계 데이터 변경을 진행한다. 6단계의 읽기 전용 로그 점검은 첫 묶음과 함께 할 수 있다.

코드 수정 시 CLAUDE.md에 따라 node --check, npm run check, git diff --check와 lib/api 변경의 전체 check 회귀를 수행한다. 스키마 변경은 재실행 가능한 SQL을 준비하고 실행 여부를 확인한다. 운영 데이터 UPDATE/DELETE 전 대상 SELECT를 확인한다. 이 계획 작성은 운영 변경 실행을 뜻하지 않는다.

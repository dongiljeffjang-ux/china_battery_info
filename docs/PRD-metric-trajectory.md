# PRD — 기업 정량 궤적 대시보드 (연차보고서 핵심사실 개편)

작성: 2026-09-08 · 상태: **초안, 브레인스토밍용** · 범위: 기업 페이지의 `연차보고서 핵심사실` 영역 대체

> 이 문서는 확정 요구가 아니라 논의를 붙이기 위한 판이다. 합의된 항목은 `prd.md`로 올리고,
> 데이터 구조가 정해지면 `data-model.md`에, 파이프라인이 정해지면 `architecture.md`에 반영한다.
> 값이 명시된 곳은 2026-09-08 운영 DB에서 실제로 센 값이다. 추정은 "추정"이라고 적었다.

---

## 1. 문제

기업 페이지의 `연차보고서 핵심사실`은 지금 **보고서별 사실 카드 목록**이다(`3c6f76d`에서 제목+사실
300자로 확장). 한 보고서 안의 사실은 잘 보이지만, **같은 지표가 해마다 어떻게 움직였는지는 보이지 않는다.**
매출 614.7억(EVE 2025)이 전년보다 큰지 작은지는 문장 안의 "26.44% 증가"를 사람이 읽어야만 안다.
회사 간 비교는 더 어렵다.

동시에 정량 흐름만 그리면 **왜 꺾였는지**가 사라진다. 매출이 꺾인 해에 어떤 고객을 잃었는지,
증설이 언제 착공됐는지는 사실 카드에만 있고 차트에는 없다.

## 2. 목표

1. 회사별 **핵심 정량 지표를 좌→우 시간축**으로 따라갈 수 있다.
2. 그 시간축 위에 **사건 플래그**를 꽂아, 수치가 움직인 구간에서 무슨 발표·계약·증설이 있었는지
   클릭 한 번으로 원문 근거까지 확인한다.
3. 모든 수치와 플래그는 **출처 보고서 URL과 원문 발췌**를 유지한다.

### 재료 경계 (2026-09-08 확정)

- **정기보고서만 쓴다.** `evidence_kind ∈ {annual_report, periodic_report}`. 정량 밴드도 플래그도
  같은 출처에서 나온다. 뉴스(`article` 130건)·웹 백필(`web_backfill` 81건)·거래소 단건 공시
  (`disclosure` 5건)는 이 화면의 재료가 아니다.
  - 근거: 한 화면 안에서 출처 등급이 섞이면 "이 꺾임이 감사받은 숫자인가 기사인가"를 사용자가
    구분할 수 없다. 뉴스 플래그는 기존 기업 시계열 매트릭스가 이미 담당한다.
- **대상은 정기보고서가 수집되는 상장사 25개사뿐이다.** 비상장 7사(Reshine, Kaijin 등)는
  **지금의 사실 카드 형태를 그대로 유지**하고 이 대시보드를 붙이지 않는다. 회사별로 화면이
  갈리므로, 재료가 없는 회사에 빈 차트를 보여 주는 상황이 생기지 않는다.

### 비목표

- 예측·전망·목표주가·투자 판단 (`CLAUDE.md` 불변조건)
- **파생 계산 지표**. 평균판매단가(매출÷출하량), CAGR, 우리가 계산한 증감률·마진율은 만들지 않는다.
  전년비 증감률은 **원문에 적혀 있을 때만** 사실로 싣는다.
- 통화 환산(위안→원/달러). 원문 통화 그대로 표시한다.
- 인접 소재사·OEM으로의 확장 (MVP 제외)

**따라서 이 프로젝트의 본질은 화면 작업이 아니라 "한국어 문장 → 숫자 열" 채우기다.**

## 4. 사용자 시나리오

1. **추세 확인** — 분석가가 Ronbay 페이지를 연다. 매출 막대가 2024→2025 우상향인데 순이익 라인만
   2025년에 음수로 꺾인 것을 3초 만에 본다.
2. **원인 탐색** — 꺾인 구간 바로 아래 플래그 3개가 보인다. 하나를 누르면 "순손실 1.87억 위안·적자 전환"
   사실 카드와 연차보고서 원문 링크가 열린다.
3. **물량-금액 대조** — Sunwoda에서 출하량(42.72GWh, +68.9%)은 급증했는데 매출 증가는 12.9%인 것을
   두 밴드를 위아래로 나란히 보고 확인한다. (해석은 사용자가 한다. 서비스는 단가를 계산해 주지 않는다.)
4. **근거 인용** — 보고서에 쓸 문장을 위해 각 점의 원문 발췌와 URL을 그대로 복사한다.

## 5. 지표 사전

`metric` 키는 코드 상수로 고정한다. 자유 문자열이면 `revenue`/`operating_revenue`처럼 표기가 흔들려
시계열이 끊긴다.

### 티어 A — 기본 노출 (거의 모든 회사·연도에 존재)

| key | 원문 항목 | 단위 |
|---|---|---|
| `revenue_total` | 营业总收入 / 营业收入 | CNY_100M |
| `revenue_main` | 主营业务收入 | CNY_100M |
| `net_profit_attr` | 归属于上市公司股东的净利润 | CNY_100M |
| `net_profit_excl` | 扣非净利润 | CNY_100M |
| `operating_profit` | 营业利润 | CNY_100M |
| `ocf` | 经营活动产生的现金流量净额 | CNY_100M |

### 티어 B — 배터리 산업 고유 (있는 회사만, 이 서비스의 차별점)

| key | 원문 항목 | 단위 |
|---|---|---|
| `shipment` | 出货量 / 销量 | GWh, t |
| `capacity_year_end` | 产能 (연말) | GWh/yr, t/yr |
| `utilization_pct` | 产能利用率 | pct |
| `segment_revenue` | 분절 매출 (+`segment` 태그) | CNY_100M |
| `overseas_revenue_pct` | 境外收入 비중 | pct |
| `top5_customer_pct` | 前五大客户 합계 비중 | pct |
| `rnd_expense` / `rnd_ratio_pct` | 研发投入 / 占营业收入比例 | CNY_100M / pct |
| `new_orders` | 新签订单 | CNY_100M |
| `gross_margin_pct` | 毛利率 (**원문 명시 시에만**) | pct |
| `patents_cumulative` / `headcount` | 累计专利 / 员工人数 | units |

### 공통 필드

`company_id, period(2025 / 2025H1 / 2025Q3), metric, value, unit, currency, line_item_zh,
yoy_pct_stated(원문 명시 증감률, 없으면 null), excerpt, source_url, report_kind, confidence`

`line_item_zh`를 반드시 남긴다 — 표본 12건에서 이미 `营业总收入`·`营业收入`·`主营业务收入`이 섞여
있었다. 한 선으로 뭉개면 회사 간 비교가 조용히 틀어진다.

## 6. 화면 — "정량 궤적 + 사건 플래그"

기업 페이지에서 기존 사실 카드(`#snapshot-grid`)의 **위**에 놓는다. 카드는 남긴다(플래그의 착지 지점).

```
 지표 칩: [매출] [순이익] [출하량] [생산능력] …        기간: 2023 ─────── 2026        출처: 정기보고서

 금액 밴드   ┃ ▇        ▇▇       ▇▇▇      ▇▇        매출(막대) / 순이익(라인)
            ┃      ╲___╱      ╲______              점선 = 반기·분기(누적)
 ───────────┼──────────────────────────────────→  공유 시간축
 시장 플래그 ▲   ▲          ▲▲         ▲          고객·수주·증설·투자
 기술 플래그 ▼        ▼            ▼               소재·공정·인증·양산
 물량 밴드   ┃ ▁▁    ▃▃▃      ▅▅▅▅    ▆▆          출하 GWh / 캐파 t (별도 축)
```

### 상호작용

- 플래그 클릭 → 사실 카드 패널(제목·`fact_ko`·원문 발췌·매체·날짜·원문 링크). 기존 digest 카드 재사용.
- 데이터 점 hover → 값 + `line_item_zh` + 원문 발췌 + 보고서 링크.
- 지표 칩 토글로 밴드 구성 변경. 기본은 매출+순이익.
- 플래그 레인 필터: 전체 / 시장 / 기술. 밀도가 실측상 낮아(6절) 기본은 전부 펼친다.

### 표시 규칙 (불변조건)

1. **결측은 선을 잇지 않는다.** 빈 구간은 "실적이 없었다"가 아니라 "아직 수집·추출되지 않았다"이며,
   매트릭스의 `EMPTY_CELL_NOTE`와 같은 문구를 쓴다.
2. **연간과 반기·분기를 같은 실선에 섞지 않는다.** 연차=실선/막대, 반기·분기=옅은 점선 + `누적` 배지.
   2026년은 아직 반기뿐이라(연차 4건·3개사) 같은 축 실선으로 그리면 급락으로 오독된다.
3. **모든 점·플래그는 원문 링크를 가진다.** 링크를 못 붙이는 값은 화면에 올리지 않는다.
4. **파생값 0건.** 화면에 뜬 모든 숫자는 원문 문자열에서 온 것이어야 한다.
5. **통화·회계기준 표기.** HKEX 상장사(CALB 등)는 영문판·다른 통화·기준일 수 있으므로 배지로 구분.

### 플래그 소스와 밀도

플래그는 새로 만들지 않고 **정기보고서 출처 `event` 535건**을 쓴다 — `layer_key`로 시장/기술 레인을
가르고, `app/app.js`의 `importanceOf()`를 그대로 재사용해 상위만 노출한다.

밀도는 실측했다(회사-연 기준 중앙값): 2023년 **1건**, 2024년 4건, 2025년 **8건**, 2026년 4건.
최대는 37건(2026년 한 회사). 즉 **겹침 문제는 2025년 이후에만 생긴다.** 기본은 전부 펼치고,
한 구간에 5건을 넘을 때만 **클러스터 핀(+N)**으로 접는다. 상위 N 고정 노출은 필요 없다.

반대로 **2023년은 플래그가 거의 없다(중앙값 1건).** 시간축 왼쪽 끝이 비는 것은 그 해에 사건이
없어서가 아니라 2023년 연차보고서 수집이 32건(23개사)뿐이기 때문이다. 화면에 그 이유를 적는다.

레인 배정은 실측 분포로 성립한다 — 시장 380건(실적 198·투자생산 104·고객 44·해외 34),
기술 147건(개발 59·IP표준 36·공정 27·소재 24). `layer_key`가 null인 7건(1개사)은 트랙만 쓴다.

**시간 해상도 차이**: 이벤트는 실제 날짜(일)에 꽂고, 지표는 기간(연/반기)의 **구간 끝**에 놓는다.
연차보고서 이벤트의 `occurred_at`이 이미 `2025-12-31`(기간 끝)로 들어와 있어 일관된다.

## 7-0. P0 실측 결과 (2026-09-08, 외부 호출 0)

정규식(C안)을 정기보고서 이벤트 535건에 돌려 **재현율과 정밀도를 따로** 쟀다.

### 재현율 — 목표를 넘는다

| 지표 | 회사-연 적중 (2023/2024/2025) | 72칸 대비 |
|---|---|---|
| 매출류 | 21 / 22 / 24 = **67** | **93%** |
| 순이익 | 12 / 17 / 23 = 52 | 72% |
| 생산능력 | 9 / 6 / 7 = 22 | 31% |
| 출하량 | 2 / 3 / 7 = **12** | **17%** |

### 정밀도 — 여기서 C안 단독이 깨진다

매출 적중 67칸 중 **권위 있는 계정 표기(`영업총수입`·`영업수입`·`영업수익`)로 잡힌 것은 23칸뿐**이고,
나머지 44칸은 `매출`이라는 두 글자만으로 잡혔다. 그중 최소 8칸은 **전사 매출이 아니었다.**

CATL 실물이 그 예다 — 정규식이 잡은 값이 연도별로 이렇다.

| 연도 | 정규식이 잡은 값 | 실제 정체 |
|---|---|---|
| 2023 | 4,009.17억 | **영업총수입 (정답)** |
| 2024 | 1,103.36억 | 해외 매출 |
| 2025 | 1,296억 | 해외 매출 |
| 2026H1 | 871.29억 | 해외 매출 |

CATL의 전사 매출 시계열을 그렸다면 2023년만 맞고 나머지는 **해외 매출을 전사 매출로 표시**했을 것이다.
차트는 아무 경고 없이 그려진다. 이것이 PRD 5절이 `line_item_zh`를 필수로 둔 이유의 실물 증거다.

원인은 정규식의 결함이 아니라 재료의 성질이다. `fact_ko`는 한국어 **요약문**이라 원문의 계정 이름
(`营业总收入` vs `境外收入`)이 "매출" 한 단어로 뭉개진다. 정규식을 아무리 다듬어도 복원되지 않는다.

### 그래서 찾은 것 — `original_excerpt`가 계정 이름을 갖고 있다

| 확인 | 값 |
|---|---|
| 2023~2025 보고서 이벤트 | 421건, **전부 `original_excerpt` 보유** (평균 114자) |
| 중문 계정명 `营业总收入`/`营业收入` 포함 | 90건, **23개사** |
| 회사-연 기준 커버리지 | 2023년 17 / 2024년 18 / 2025년 22 = **57칸 (79%)** |

**계정 판정은 중문 발췌로, 숫자 읽기는 한국어 표기로** 하면 정밀도 문제가 사라진다. 이는
`lib/fact-extraction.js`의 기존 원칙("수량 표기가 발췌 안에 글자 그대로 있어야 하고 숫자는 모델이
아니라 코드가 읽는다")과 같은 방향이다.

### 권고 변경 — C안 단독 → C′ (중문 앵커 정규식)

| 안 | 판정 | 근거 |
|---|---|---|
| C (한국어 정규식 단독) | **기각** | 재현율 93%지만 계정 오판이 최소 8칸. 조용히 틀린 차트를 만든다 |
| **C′ (중문 발췌로 계정 판정 + 한국어 표기로 수치 추출)** | **채택** | 외부 호출 0, 매출 57칸(79%) 확보 |
| B (LLM 전용 추출) | **보류, 잔여분에만** | C′가 못 채운 15칸과 티어 B 지표(출하 17%·캐파 31%)에 한정 |

출하량 17%·생산능력 31%는 어느 안으로도 낮다. **이 둘은 요약문에 거의 안 실린다** — 보고서 본문
(`report_digest.body_original`)까지 들어가야 하는 별개 작업이다. P3로 미룬다.

## 7. 데이터 파이프라인 — 3안과 권고 순서

| 안 | 방법 | 외부 호출 | 약점 |
|---|---|---|---|
| **A. 기존 추출기 전면 실행** | 보고서 `event` 535건에 `lib/fact-extraction.js` 백필 | LLM 535회 | `metric` 자유 문자열이라 표기 흔들림 |
| **B. 재무 전용 소형 추출** | 지표 사전(5절) 고정 스키마만 추출 → `report_metric` 테이블 | LLM 보고서당 1회(≈200회) | 새 SQL·사전 관리 |
| **C. 정규식 파싱** | 한국어로 정규화된 `fact_ko`에서 `억 위안`·`GWh`·`%` 표기 추출 | **0** | 항목 구분(营业收入 vs 主营业务收入) 취약 |

**권고: C로 먼저 커버리지를 측정하고, 그 숫자를 보고 B를 확정한다.**
C는 비용이 0이므로 "회사 25 × 연도 4 칸 중 몇 칸이 채워지나"를 즉시 셀 수 있다.
`CLAUDE.md` 진단 규칙("제약이 실제로 구속력을 갖는지 먼저 센다")을 그대로 적용한 순서다.
A는 B와 중복 투자다. 어느 안이든 `lib/fact-extraction.js`의 **"수량 표기가 발췌 안에 글자 그대로
있어야 하고 숫자는 모델이 아니라 코드가 읽는다"** 원칙을 그대로 계승한다.

### 저장

새 테이블 `report_metric`(5절 공통 필드)을 권한다. `event_fact`는 이벤트 단위라 회사×기간×지표 피벗에
매번 조인·중복 제거가 붙는다. 재실행 가능한 SQL을 `supabase/`에 추가하고 SQL Editor 실행은 사용자에게 확인.

### API

**새 `api/*.js` 파일을 만들지 않는다** (Vercel Hobby 함수 수 가드레일). `api/company.js`에
`?view=metrics`를 얹어 `{metrics:[…], flags:[…]}`를 한 번에 준다.

## 9. 단계

각 단계는 **다음 단계로 넘어가기 전 통과해야 할 게이트**를 갖는다. 게이트에서 막히면 그 자리에서
사용자에게 보고하고 방향을 정한다 — 막힌 채로 다음 단계를 쌓지 않는다.

### P0 — 커버리지 실측 ✅ 완료 (2026-09-08, 외부 호출 0)

결과 7-0절. C안 단독 기각, **C′(중문 앵커) 채택**. 매출 상한 57칸(79%) 확인.

### P1 — 추출기와 저장 (외부 호출 0, LLM 없음)

1. `lib/report-metrics.js` 신규: `original_excerpt`의 중문 계정명으로 `metric` 판정 →
   `fact_ko`/`quantity_text`에서 숫자 문자열 추출 → `{metric, value, unit, line_item_zh,
   yoy_pct_stated, excerpt}`. **숫자는 코드가 표기에서 읽고, 계정 미상이면 버린다.**
2. `scripts/check-report-metrics.mjs` 회귀: 계정 판정(해외 매출을 전사 매출로 읽지 않을 것 —
   CATL 2024·2025가 고정 케이스), 억/만 스케일, 음수(적자), 기간 정규화, 네트워크 없이 통과.
3. `supabase/report-metric.sql` (재실행 가능) → **SQL Editor 실행은 사용자 확인 후.**
4. 백필 1회 실행 후 실제 채움 수를 센다.

**게이트 P1**: 매출 **50칸 이상**(예상 57), 계정 미상으로 버린 값 0건, 회귀 전부 통과.
못 넘기면 잔여분에만 B안(LLM)을 붙일지 판단한다.

### P2 — 화면 1차

`api/company.js`에 `?view=metrics` 추가(새 API 파일 없음) → 금액 밴드(매출 막대 + 순이익 라인)
+ 시장/기술 플래그 레인 + 기존 사실 카드 연동. 비상장 7사는 분기해 현행 카드만 렌더.

**게이트 P2**: 25개사를 눈으로 훑어 축·결측·연간/반기 표기가 오독을 만들지 않는지 확인.
`preview_start`로 마크업 확인(CSS는 회귀가 안 잡는다 — `HANDOFF-CODEX.md` 8절).

### P3 — 물량 밴드 (여기서만 LLM 검토)

출하 17%·캐파 31%는 요약문에 거의 없다. `report_digest.body_original`(전 이벤트 보유)에서
产销量 표를 읽어야 하고, **표 오독 잔여 문제**(10절)와 정면으로 만난다. 착수 전 비용·정확도를
따로 측정하고 사용자 승인을 받는다.

### P4 — 기업 비교

지표 1개 × 다중 회사 랭킹(연도 슬라이더). P2가 안정된 뒤.

## 9-1. P1에서 드러난 더 큰 구멍 — 요약 단계가 전사 매출을 빼먹는다

추출기를 만들다 사용자가 짚었다: "한국어로 파싱이 안 됐다면 서비스에도 안 나온 것 아니냐."
맞다. 세어 보니 **연차보고서 72 회사-연 중 19칸에는 전사 매출이 아예 없다.** CATL 2024·2025가
그 안에 있다. 화면이 잘못 보여 준 게 아니라, `digestReport`가 보고서에서 사실 수십 건을 고를 때
`营业总收入`을 안 고른 것이다. 추출기가 아니라 **수집 단계의 결함**이다.

- 지금까지 안 보였던 이유: 사실 카드는 있는 것만 나열하므로 없는 항목은 티가 안 난다.
  시계열 대시보드는 빈 칸으로 그 구멍을 드러낸다. 이 프로젝트의 부수 효과 중 가장 값진 부분이다.
- 대응(P1.5, 별도 작업): 정기보고서 요약 프롬프트에 **티어 A 계정은 발췌에 있으면 반드시 한 건으로
  낸다**는 규칙을 넣고, 서버가 연차보고서 요약 결과에 `revenue_total`이 없으면 로그로 남긴다.
  `ac83ef3`의 한국어 강제와 같은 방식 — 프롬프트만 고치면 재발하므로 서버 검사를 같이 둔다.
- 재수집 비용이 있으므로 착수 전 사용자 승인을 받는다.

## 10. 알려진 위험

- **표 오독 잔여 문제**(`HANDOFF-CODEX.md` 5번 4항): 여러 줄 셀이 y좌표 묶기에서 흩어진다.
  R&D·产销存 표에서 나오는 티어 B 지표는 정확도가 낮을 것으로 **추정**한다. P3에서 별도 검증.
- 2026년 연차보고서 이벤트는 4건·3개사뿐 → 2026 칸은 당분간 반기로만 채워진다.
- **2023년 구간이 얇다.** 보고서 이벤트가 회사-연 중앙값 1건이라 시간축 왼쪽 끝은 매출 점 하나에
   플래그가 거의 없는 상태가 된다. 3년 추세를 보여 주겠다는 약속이 왼쪽에서 부실해 보일 수 있다.
   대응: 기본 범위를 2024~2026으로 두고 2023은 토글로 확장하는 안을 검토한다(미결 6번).
- 비상장 7사(Reshine, Kaijin 등)는 **대상에서 제외**되어 기존 사실 카드를 유지한다. 회사에 따라
   화면 구성이 달라지므로, 카드만 있는 회사에 "정기보고서 미수집" 사유를 한 줄로 표시한다.
- `report_chunk` 임베딩 0건(같은 문서 5번 6항)이라, 보고서 원문 재질의로 값을 보강하는 경로는 아직 없다.

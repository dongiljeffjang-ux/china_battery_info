# 분석 페이지 검색 적합성 개선 — 실행 가이드

작성일: 2026-09-09. 다른 모델이 작업을 인수할 때 이 문서부터 작업 범위를 확인한다.

## 목표와 권한

질문의 회사·기간·주제·관계에 맞는 근거와 답변을 제공하고, 정답 근거가 부족하면 그 부족을 정확히 표시한다. 검색 결과 수를 줄여 정확도만 높이는 대신, 저장돼 있는 정답을 찾는 능력도 함께 개선한다.

이 문서는 실행 계획이다. 문서 작성 요청 자체가 운영 DB 변경·유료 재처리·배포 승인은 아니다. 실행 요청을 받으면 해당 요청과 기존 승인 범위 안에서 진행한다.

## 시작할 때 읽을 것

1. `../CLAUDE.md`: 저장소 작업 지침의 단일 출처.
2. `HANDOFF-CODEX.md` 최신 항목과 `HANDOFF.md`: 배포·운영 작업·막힘 상태. 충돌하면 최신 확인 기록을 우선한다.
3. `PLAN-embedding-recovery.md`: 이미 구현된 작업과 재처리 경로. 기존 T1~T15를 새로 구현하기 전에 완료 여부를 확인한다.
4. 구현 단계에서 `../prd.md`, `../data-model.md`, `../architecture.md`의 관련 절을 읽는다.

`git status --short`로 기존 변경을 확인한다. 계획서의 과거 수치를 현재 운영 수치로 보고하지 않는다. 키 값은 출력하지 않는다.

## 출발점: 확인된 코드와 과거 실측 구분

- 코드 확인: `lib/knowledge-search.js`는 단어·의미 검색을 합친 뒤 회사 언급과 기사별 청크 수로 순서를 조정한다. 다른 회사 근거는 삭제하지 않아 후보가 부족하면 최종 목록에 들어갈 수 있다.
- 코드 확인: 일반 검색 RPC 호출에는 질문의 기간 조건이 없다. 정량 질문은 `lib/metric-lookup.js`에서 회사·기간·지표를 별도 조회한다.
- 코드 확인: 각 검색기 후보는 현재 10건이다. 이 수가 정답 누락의 원인인지는 후보별 순위를 측정해서 판단한다.
- 인수인계 실측: 개선 전 사람 판정 42건의 정밀도 0.34, 기존 기사 227건 재구성 대기, 다중 회사 기사 95건. 이번 실행에서 상태를 다시 확인한다.
- 재구성만으로 모든 문제가 해결되는지, 별도 재순위 모델이 필요한지는 아직 미확정이다.

## 1. 평가 질문과 실패 지점 고정

기존 T6 5문항을 유지하고 아래 유형을 포함해 15~20문항을 만든다. 실제 사용자 실패 질문을 우선하며 기대 답은 저장된 근거로 확인한다.

- 단일 회사의 정량 값: CATL 2025년 매출 등.
- 회사·기간·주제를 함께 묻는 질문: 파라시스 2026년 상반기 신규 고객 등.
- 두 회사의 관계: Reshine과 CATL 협력 등.
- 복수 회사 각각의 비교: 두 회사가 같은 청크에 함께 등장해야 한다는 조건을 걸면 안 되는 사례.
- 회사 미지정 산업 질문: 전고체 배터리 양산 시점 등.
- 정답 부재·별칭·화면 회사 필터와 질문 회사가 충돌하는 사례.

문항마다 질문, 화면 필터, 기대 조건, 확인된 정답 근거 ID·발췌, 정답 존재 여부, 판정 이유를 저장한다. 일부 문항은 조정에 사용하지 않는 최종 검증용으로 남긴다. 사람 판정과 모델 잠정 판정을 구분한다.

검색 후보 → 최종 근거 → 답변을 나누어 기록한다. 실패를 데이터 미저장 / 후보 누락 / 순위 밀림 / 무관 근거 통과 / 답변 오독 중 하나 이상으로 분류한다.

**완료 기준:** 고정 문항과 근거 판정표, 현재 실행 결과, 실패 유형별 건수가 재현 가능한 파일로 남는다. 운영 접근이 막히면 문항·로컬 평가 틀을 준비하고 운영 기준선은 미측정으로 표시한다.

## 2. 저장 데이터 정비

기존 스크립트 `scripts/restructure-article-chunks.mjs`와 `scripts/reembed-events.mjs`를 읽고 기본 실행의 쓰기·외부 API 호출 여부부터 확인한다. 기사 청크 재구성과 사건 시점 보강은 별도 작업으로 측정한다.

운영 적용 전 대상 ID·source_type·건수와 전후 예시를 확인하고 복구 가능한 사본 또는 검증된 복구 경로를 확보한다. 실제 키가 필요한 작업은 환경 준비 상태를 확인한다. 새 데이터 저장 성공 후 해당 옛 조각만 교체하는 기존 안전 조건을 유지한다.

다중 회사 검색은 `article_company` 연결을 근거로 설계한다. `company_ids` 배열은 후보안이며 조인 방식과 비교해 결정한다. 기사에 연결된 회사 전체가 모든 청크의 주제인 것은 아니므로, 기사 수준 귀속은 후보 확보에 쓰고 청크 내용 적합성도 확인한다. 기사 없는 이벤트·보고서 청크의 귀속과 기존 단일 회사 필터 호환성을 포함한다.

스키마 변경이 필요하면 재실행 가능한 SQL과 대상 조회·검증·복구 절차를 먼저 작성하고 저장소 지침에 따라 운영 실행을 확인한다. T8 단위 파싱 수정·검증 전 `backfill-report-metrics.mjs --write`는 실행하지 않는다.

**완료 기준:** 적용 범위·건수·누락 여부·재실행 안전성을 확인하고, 1단계 문항으로 데이터 정비만의 효과를 기록한다. 코드 완료와 운영 적용 완료를 별도 표시한다.

## 3. 질문 조건과 검색 경로 구현

질문을 회사, 기간, 주제/지표, 질문 유형으로 해석하는 명시적 구조를 만든다. 확실한 조건과 해석이 불확실한 조건을 구분한다. 화면 회사 선택과 질문이 충돌할 때의 동작을 명시하고 시험한다.

- 정량: 기존 표 조회를 재사용하고 요청 기간·지표·회사와 반환 행의 일치를 검증한다.
- 서술: 회사·기간·주제를 검색에 반영한다. 사건 발생 시점과 기사 게시일·보고 기간을 구분한다. 날짜 불명은 기간 불일치로 단정하지 않는다.
- 관계: 주체·상대 회사와 실제 관계를 확인한다. 이름 두 개의 동시 등장만으로 협력 관계라고 판단하지 않는다.
- 비교: 회사별로 근거를 확보한다. 모든 회사가 한 청크에 등장하도록 강제하지 않는다.
- 산업 질문: 회사가 명시되지 않아도 다양한 회사의 관련 근거를 확보한다.

후보 수와 검색 가중치는 정답의 후보 진입 여부를 측정한 뒤 변경한다. 검색 조건 강화로 공급사·계열사 정답이 잘리지 않는지 확인한다.

**완료 기준:** 질문 유형별 동작 시험이 통과하고, 각 결과의 채택·탈락 조건을 추적할 수 있다. 2단계 대비 후보 정답 확보율과 누락 문항 변화를 기록한다.

## 4. 근거 적합성 및 답변 검증

후보마다 질문 조건 충족 여부를 확인하는 단계를 둔다. 명확한 회사·기간·주제 불일치는 탈락시키고, 불확실성과 근거 부족을 구분한다. 적합한 근거만 최종 답변에 넘기며 부족한 수를 무관한 결과로 채우지 않는다.

규칙만으로 판정하기 어려운 사례가 평가에서 남으면 재순위 모델을 비교 실험한다. 도입 여부는 정확도·정답 누락·응답 시간·비용 변화로 결정한다. 점수 임계값은 평가 데이터로 정하고 검증용 문항에도 적용한다.

최종 답변의 회사·시점·수치·관계가 인용 근거로 뒷받침되는지 확인한다. 근거가 없다는 답과 실제 사실이 존재하지 않는다는 답을 구분한다. 검색 경로 장애가 근거 부재로 잘못 표시되는지도 시험한다.

**완료 기준:** 무관 근거 탈락, 정답 보존, 근거 부족 안내, 인용 정합성을 실제 사례와 회귀 시험으로 확인한다. 3단계 대비 변화를 기록한다.

## 5. 최종 평가와 배포 인계

동일 데이터·질문·옵션에서 전후를 비교한다. 문항별 표에 다음을 기록한다.

- 반환 근거 정밀도: 적합 근거 수 / 반환 근거 수. 0건은 별도 표기한다.
- 정답 확보: 알려진 정답이 있는 문항 중 하나 이상의 정답 근거를 최종 결과에서 확보한 비율. 전체 코퍼스 재현율로 부르지 않는다.
- 조건 위반: 다른 회사·기간·주제의 근거가 최종 결과에 포함된 건수.
- 답변 정합성: 근거 없는 핵심 주장 수, 인용으로 확인 가능한 답변 여부.
- 응답 시간과 외부 호출 비용 또는 추정 호출량.

권장 출시 기준은 고정 문항에서 명백한 조건 위반과 근거 없는 핵심 주장 0건, 기준선 대비 정답 확보율 비하락 및 정밀도 개선이다. 이 기준은 프로젝트 제안값으로 기록하고 실제 측정값과 함께 판단한다. 달성하지 못하면 남은 실패 문항과 이유를 공개한다.

수정 파일에 맞춰 `CLAUDE.md`의 필수 검사를 실행한다. UI를 바꿨으면 실제 표시도 확인한다. 배포는 기존 GitHub main → Vercel 경로와 승인 범위를 따른다. 승인 대기 전 코드·SQL·평가 결과·복구 절차를 검토 가능한 상태로 완성한다.

**완료 기준:** 전후 평가와 검사 결과, 운영 적용 내역, 남은 실패 문항, 배포 후 고정 질문 확인 결과가 남는다. 운영 검증 전에는 작업 전체를 완료로 보고하지 않는다.

## 진행 기록과 막힘 처리

후속 실행자는 이 문서 아래 진행 표를 갱신하고 상세 평가 결과 파일을 연결한다. `HANDOFF-CODEX.md`에는 해당 결과의 링크와 다음 행동만 짧게 남긴다.

| 단계 | 상태 | 결과 파일·증거 | 다음 행동 |
|---|---|---|---|
| 1. 기준선 | 진행 중 | 기존 T6 5문항·과거 42건 판정은 확인. 확장 문항과 현재 운영 재측정은 미완료 | 정답 근거를 연결한 15~20문항 평가표 작성 |
| 2. 데이터 | 미착수 | — | 현재 적용 상태와 대상 확인 |
| 3. 검색 | 일부 완료 | 명시 기간 우선 정렬 구현·로컬 회귀 (`check-hybrid-search.mjs`). 운영 결과 미측정 | 관계·주제 조건의 적합성 규칙과 후보 측정 |
| 4. 적합성 | 미착수 | — | 조건별 채택·탈락 시험 |
| 5. 검증·배포 | 미착수 | — | 동일 문항 전후 평가 |

운영 접근이 막히면 로컬 구현·가짜 네트워크 시험·SQL 작성은 진행할 수 있다. 운영 효과 측정은 보류로 남긴다. 문서 간 키 상태 설명이 충돌하므로 현재 확인 없이 유출·키 정상 여부를 단정하지 않는다. 완료 보고에는 확인한 사실, 미검증 항목, 사용자 조치가 필요한 정확한 작업을 구분한다.
